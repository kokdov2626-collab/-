# סל חכם

מנוע אופטימיזציה לסל קניות: בהינתן רשימת קניות וכתובת למשלוח, המערכת מוצאת
את העלות הכוללת הנמוכה ביותר — כולל מוצרים, משלוחים, דמי שירות והשפעת מינימום
הזמנה — גם כאשר זה דורש פיצול הקנייה בין כמה רשתות.

זהו **MVP (שלבים 1-9 מתוך 11 בתוכנית המקורית)**. הכל בקוד הזה עובד בפועל —
אין מסכי דמו ריקים — אבל הנתונים עצמם הם **DEMO DATA** (ראו סעיף למטה).

## מה עובד עכשיו (אמיתי, לא מדומה)

- **אלגוריתם אופטימיזציה אמיתי**: בודק את כל תת-הקבוצות של הרשתות (עד 4),
  מקצה כל מוצר לרשת הזולה ביותר בתוך כל תת-קבוצה, ובוחר את הזולה מכולן —
  כולל טיפול נכון במינימום הזמנה ומשלוח חינם מסכום מסוים.
  `lib/algorithm/optimize.ts`
- **9 בדיקות (Vitest) שעוברות בפועל** על התרחישים המחייבים מסעיף 41 של הספק
  המקורי: מוצר יחיד, כמה מוצרים, פיצול בין רשתות, משלוח חינם, מינימום הזמנה,
  מחיר/מוצר חסרים, רשת שלא מספקת לכתובת, ומקרה שבו 4 רשתות *לא* משתלמות.
  `npm test`
- **מנגנון Matching** שמבחין בין "חלב 1 ליטר" ל"חלב 2 ליטר", בין "ביצים L"
  ל"ביצים M" וכו' — ולא ממציא התאמה כשאין אחת טובה מספיק.
  `lib/matching/match.ts`
- **קטלוג של 108 מוצרי דמו** ו-**5 ספקי-דמו** (רמי לוי, שופרסל, יוחננוף,
  ויקטורי, קרפור) עם כיסוי מוצרים, מחירים, מבצעים ותנאי משלוח שונים לכל אחד.
  `lib/providers/`
- **API**: `POST /api/cart/calculate` בדיוק לפי המבנה שביקשת בסעיף 31.
- **ממשק משתמש** RTL/עברית/מובייל-פירסט עם מסך קלט ותוצאות (סעיפים 18-23).
- **Admin בסיסי** ב-`/admin` (סעיף 26-27) — כרגע מציג נתונים מהזיכרון.
- **סכמת Prisma מלאה** ל-PostgreSQL עם כל הטבלאות מסעיף 3, ו-seed script
  התחלתי שמכניס את הרשתות.

## מה עדיין DEMO ולא נתונים אמיתיים

- **המחירים עצמם** מיוצרים באופן דטרמיניסטי-מדומה (לא אקראי אמיתי, כך
  שהתוצאות עקביות), ומסומנים `source: DEMO` ברמת הקוד. **אין כרגע חיבור
  לשום מקור מחיר אמיתי.**
- **המסד (Prisma/PostgreSQL) עדיין לא מוזן בזמן ריצה** — חישוב הסל היום קורא
  ל-Providers בזיכרון (`lib/providers`), לא למסד. ה-seed script מכניס רק את
  שמות הרשתות, כבסיס להתחלה. חיבור מלא (Product/Price/DeliveryOption אמיתיים
  במסד + האלגוריתם קורא מהמסד) הוא הצעד הבא (שלב 2-3 בתוכנית שלך, סעיף 40).
- **אין Scheduler שרץ בפועל** (סעיף 8) — התשתית לכך (מודל `Price`,
  `PriceHistory`, `ProviderLog`) קיימת בסכמה, אבל אין job שמריץ עדכונים.
- **Admin לא מחובר למסד** — מציג רק ספירות מהזיכרון.

## איך לחבר נתוני אמת (סעיף 28-29 של הספק)

הרשתות הגדולות בישראל (רמי לוי, שופרסל, יוחננוף וכו') **לא חושפות API רשמי**
למחירים. המקור החוקי היחיד הוא **קובצי המחירון הפומביים** שכל רשת חייבת
לפרסם באתר שלה מכוח חוק שקיפות מחירים (קבצי XML/GZ, מתעדכנים כמה פעמים ביום).
כדי לחבר רשת אמיתית:

1. לממש `SupermarketProvider` חדש (`lib/providers/`) שמוריד ומפרסר את קובץ
   המחירון הפומבי של אותה רשת.
2. למפות בין ברקוד/שם המוצר בקובץ לבין `Product`/`ProductVariant` במסד.
3. לשמור את המחירים בטבלת `Price` (+ רשומה ב-`PriceHistory`), ולסמן
   `source` בשם הרשת האמיתית (לא `DEMO_*`).
4. להחליף בקריאה מה-API: להשתמש בפרובידר האמיתי במקום פרובידר הדמו.

**לא בניתי Scraper או API בדוי לאף רשת** — זה נשאר Demo Provider עד שיחובר
מקור נתונים אמיתי, בדיוק כמו שביקשת בסעיף 28.

## הפעלה מקומית

```bash
npm install
npm test          # 9 בדיקות האלגוריתם
npm run dev        # http://localhost:3000
```

חישוב הסל עובד ללא מסד נתונים בכלל (המחירים בזיכרון). כדי להתחיל לעבוד מול
מסד אמיתי:

```bash
cp .env.example .env       # והכניסו את ה-DATABASE_URL מ-Neon
npx prisma migrate dev --name init
npm run seed
```

## פריסה (Netlify + Neon)

הפרויקט הזה הוא אפליקציית **Next.js עם API routes ו-Prisma** — לא קובץ
HTML בודד. שימו לב לשני דברים לפני שמעלים ל-Netlify:

1. **מסד נתונים**: Netlify לא מריץ PostgreSQL בעצמו. פתחו פרויקט חינמי ב-
   [Neon](https://neon.tech), והדביקו את מחרוזת החיבור כמשתנה סביבה
   `DATABASE_URL` בהגדרות ה-Site ב-Netlify.
2. **Scheduler**: כשתרצו להריץ עדכוני מחירים אוטומטיים (סעיף 8), האפשרות
   הפשוטה ביותר ב-Netlify היא **Scheduled Functions** (cron מובנה), או שירות
   cron חיצוני חינמי (כמו cron-job.org) שקורא ל-endpoint ייעודי מדי X דקות.

חיבור Git רגיל ל-Netlify (Build command: `npm run build`, Publish directory:
`.next`, עם Next.js Runtime של Netlify) עובד ישירות מה-repo הזה.

## מגבלות ידועות של האלגוריתם

הבחירה בין תת-קבוצות רשתות כרגע היא בדיקה ישירה של כל 2⁵-1=31 האפשרויות —
מספיק ומיידי לחמישה ספקים. עם עשרות רשתות (כפי שציינת בסעיף 30) יש לעבור
ל-Branch and Bound או תכנות שלם (ILP) כדי לא לבדוק את כל תתי-הקבוצות באופן
נאיבי — זה לא מומש כרגע.
